## 2. 根因链（三层，主文 §3 用）

1. **抽取机制**：K1 提及抽取 = 纯词典扫描（无 LLM），词典面 = Schema
   entity_types 的主名+别名集合——Schema 词条集就是抽取面本身。
2. **词典来源**：physics / nuclear_electronics 两 Schema 由
   `corpus/gen_subject_schemas.py` 批产（LLM 起草+validator），产出的是
   **类型分类学**（4–8 个类别词别名/类），不是领域术语表。
3. **对照**：hydrogeology 手工演进 3,742 词条（78 篇 → 1,608 实体，健康）；
   说明塌缩与库规模无关，与词条性质有关。
- 监控盲区：富化任务全 DONE、吞吐正常、链接数巨大（表面繁荣）——只有
  **实体基数与名字分布**两个指标异常，均不在常规告警面。

## 4. 全链重建（rebuild_graph_enrich.py，b44cc64；性能三修）

- 清障：Nebula 顶点 WITH EDGE 删 + MySQL 四表分块删 + OS knc-entity-v2
  投影 delete_by_query；四阶段重入队 **766,501 单**（2026-10-08 队列实测）。
- 重建期暴露并修复的性能病（主文 §5 素材，均有 commit 佐证）：
  - **B90**（d81a41c）：图谱投影原句全库实体 JOIN 全库链接——单条 25min+，
    80 并发打满 MySQL 107 核/负载 500；按 doc 收窄后秒级、107→29 核；
  - **B91**（d020a3d）：links INSERT 无序 → gap 锁交叉（死锁 1213）；
    ORDER BY mention_id 固化插入序；
  - **B93**（c85f5b3）：逐 action INSERT 合并单条 UNION ALL INSERT-SELECT，
    死锁清零；
  - **B94**（c85f5b3）：_alias_canonicals O(N²) 缩写比对按 schema 签名缓存，
    101s→0.05s——富词典放大了 N²，16 线程全在 GIL 排队；
    实测 links 8/min→1,100/min（137×）。
  - **B95**（f0141da，2026-10-08 晚）：B93 单语句写入**参数错序**——SQL 首位
    `%s` 是 `UNHEX(kb)`，调用却把 form 传到首位 → `UNHEX('alloy')`→NULL →
    kb_id 非空违约被 INSERT IGNORE 整批静默吞行。表象全绿（任务 DONE、
    实体照建、吞吐 1,100/min），唯一暴露面 = registry 零增长。KB1 自
    11:41 起零插入（7h 白跑）、KB2 全程零行；无效果 DONE links 重置回
    PENDING：KB1 51,459 + KB2 24,372。修复后实测 **+61 万行/60s**
    （KB1 2,029,171→3,015,748）。另：18120 曾因 MySQL 半开连接
    （ping 无 read_timeout）整实例假活——py-spy 定位 wedged 线程。
